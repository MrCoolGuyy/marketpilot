# MarketPilot Architecture Decision Records (ADR)

This document captures the fundamental, unchangeable design choices that form the backbone of MarketPilot's architecture. It exists to prevent future maintainers from accidentally breaking the system's structural integrity by introducing "quick fixes."

## 1. The Thin Orchestrator (Event Bus)
- **Decision**: The TradingPipeline contains ZERO trading logic. It merely acts as a router that subscribes to an async EventBus.
- **Reasoning**: Decoupling. The Scanner Engine should not know the Strategy Engine exists. By using a strict, sequentially-ordered Event Bus (CycleStarted -> ScannerFinished -> etc.), we guarantee determinism and make each engine 100% unit-testable in isolation.

## 2. Immutable Event Payloads & TradePlans
- **Decision**: All event payloads and core domain models (e.g., TradePlan, StrategyResult) are strictly immutable (pydantic.BaseModel with rozen=True).
- **Reasoning**: State mutations cause the most insidious bugs in concurrent trading systems. If the Risk Engine wants to modify a TradePlan, it must return a *new* instance. The Execution Engine receives an unalterable contract.

## 3. The Journal as the Single Source of Truth
- **Decision**: The Performance & Research Engine derives all metrics (Sharpe, Drawdown, Feature Importance) directly from the TradeExecutionRecord stored in the Journal.
- **Reasoning**: Caches drift. Databases can become desynchronized. The Journal is the final append-only cryptographic ledger of what the bot *actually* did. If it's not in the Journal, it didn't happen.

## 4. Separation of Core and Research Dependencies
- **Decision**: marketpilot-core has minimal dependencies (No pandas, scipy, etc.). Heavy data science libraries are strictly isolated to marketpilot-research (via optional dependencies).
- **Reasoning**: The trading daemon must be ultra-lightweight, start instantly, and minimize points of failure (e.g., C-extension crashes). Research requires heavy math. They must not share the same memory space constraints.

## 5. Configuration Freeze During Campaigns
- **Decision**: Once a Paper Trading or Live campaign begins, the config_hash is locked. No strategy parameters (EMA, ATR, thresholds) may be tuned.
- **Reasoning**: Changing parameters mid-campaign destroys dataset homogeneity. A 90-day dataset with 3 different threshold tweaks is statistically useless for Monte Carlo simulation or Feature Importance analysis.

## 6. Delayed Dashboard Implementation
- **Decision**: Phase 6 (Dashboard) was deliberately postponed until after Phase 8 (Paper Trading) and Phase 9 (Research Governance).
- **Reasoning**: A UI is useless without empirical data. By forcing the system to run headless first and generate Parquet datasets, the resulting Dashboard becomes a true Research Platform (showing actual Expectancy, Calmar, and Drift) rather than just an empty visual wrapper.

## 7. Architecture Status
**Core Architecture Frozen.** Beginning with Release Candidate RC-1, MarketPilot shall evolve only through evidence generated by the Research Platform. Any modification to trading logic, risk policy, execution behavior, or configuration must be justified by reproducible empirical results and approved through the established Research Governance process.
